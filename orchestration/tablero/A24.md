## Por qué

Emilio, 03-09, dos veces y la segunda en mayúsculas: *"PERO TE DIJE QUE ESTO DEBE SER 100% AUTÓNOMO
24/7 Y AUTOSUFICIENTE, DEBERÍA HABERSE REINICIADO"*. Y antes: *"el propio sistema de Ultrarentable
debe monitorizarlo, su backend o lo que sea"*.

Hoy ha pasado dos veces esto: la API local (`127.0.0.1:8100`) se muere y **nadie la vuelve a
levantar**, así que la web se queda enseñando cosas falsas:

```
$ curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8100/api/v1/discovery/status
000          (no responde: proceso muerto)
```

Y Emilio ve en pantalla, a la vez:
- `/estrategias` → *"No se pudo conectar con la API: API Request Error (500 /api/v1/discovery/status)"*
- `/trading-desk` → *"ESTADO: DESCONECTADO — Error al consultar estado del gateway (HTTP 500)"*
- la cabecera → `MOTOR: NO DISPONIBLE`

En el servidor de StrategyQuant esto ya está resuelto: cada pieza es una unidad de systemd con
`Restart=always` y `enable`, y hay un supervisor (`services/ops/supervisor_ultrarentable.py`) que
cada minuto comprueba, arregla y publica `salud.json`. **En el PC no hay nada de eso.** Ese es el
agujero que cierras aquí.

## Qué hacer

**1. Que la instancia local se levante sola.** Sin scripts sueltos que haya que acordarse de
arrancar: dentro del propio sistema. La vía es `scripts/orq/web_local.ps1`, que ya sabe arrancar la
API y la web; añádele un modo de vigilancia y regístralo como **tarea programada de Windows** que
arranque al iniciar sesión y se repita cada pocos minutos, con `MultipleInstances IgnoreNew` para que
no se dupliquen. Debe comprobar y, si hace falta, relanzar:
   - la API en `127.0.0.1:8100` (con `SQX_API_URL`, `M1_ESTADO_URL` y `M1_ESTADO_AUTH` puestas: mira
     cómo lo hace hoy la línea de `uvicorn` en ese mismo script);
   - la web en `127.0.0.1:3100`, **solo si no hay nadie escuchando ya** en ese puerto. El IDE de
     Emilio levanta a veces su propio `next dev` ahí: si hay alguien, no se toca. Nunca matar un
     proceso que no hayas arrancado tú.

**2. Que la web no mienta cuando la API no está.** Hoy `/estrategias` y `/trading-desk` pintan un
error rojo enorme. Que digan lo que pasa, en llano y en gris, sin alarmismo: *"El servicio local no
responde. Se está reintentando solo."* Nada de "500 Internal Server Error" en la cara del usuario.

**3. Una página que diga si el sistema está en pie.** Añade a `/sistema` (o crea la sección si no
existe) un bloque **"¿Está todo funcionando?"** que consuma `GET /api/v2/m1/salud`. Ese endpoint ya
existe y devuelve, medido cada minuto por el supervisor del servidor: StrategyQuant, el bucle de
celdas, el publicador de estado, la celda en curso, disco, memoria y carga. Píntalo como una lista de
piezas con su estado y su detalle, en grises, verde/rojo solo para bien/mal. Si el endpoint no
responde, se dice; no se inventa un "todo bien".

Ejemplo de lo que devuelve hoy (comprobado):

```json
{"todo_en_pie": true,
 "piezas": {"strategyquant": {"ok": true, "detalle": "25 proyectos FONDEO"},
            "m1-runner": {"ok": true, "detalle": "activa"},
            "celda_en_curso": {"ok": true, "detalle": "FONDEO_MNQ_H1, minutos sin avanzar: None"},
            "disco": {"ok": true, "detalle": "87.6 % libre (185 GB de 211 GB)"}}}
```

## Aceptación

```bash
# 1. Con la API viva, responde:
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8100/api/v2/m1/salud     # 200
# 2. Se mata a mano y vuelve sola en menos de 5 minutos (dilo con las dos horas medidas):
#    (mata el proceso de uvicorn del 8100, espera, y vuelve a llamar al mismo curl -> 200)
# 3. La tarea programada existe:
powershell -NoProfile -Command "Get-ScheduledTask -TaskName '*ltrarentable*' | Select-Object TaskName,State"
# 4. Tipos:
cd apps/web && ../../node_modules/.bin/tsc --noEmit -p tsconfig.json               # rc=0
```

En el parte, pega **la prueba del punto 2 con sus horas**: la hora a la que la mataste y la hora a la
que volvió sola. Es la única que demuestra que el agujero está cerrado.

arriba (regla de Emilio: un solo menú, el lateral).
