## Por qué

En el servidor Oracle sigue corriendo la instalación vieja de StrategyQuant, y está haciendo daño
sin dar nada a cambio. Medido y documentado en el propio repositorio:

- `orchestration/ops/systemd/sqx.service.d-override.conf:5-9` (escrito el 01-09):
  *"sqcli sostiene 113-116 % de CPU y 4,3 GB de RAM de forma continua, y el 2026-09-01 llevaba 37
  ciclos de build con «Aceptado: 0» — es decir, consumía la mitad de la máquina sin producir una sola
  estrategia utilizable, porque su configuración apunta a un único símbolo (AUDUSD_H1) con un OOS del
  0,3 %."*
- El orquestador lo confirmó el 2026-09-03: el proceso `sqcli` llevaba **más de un día y medio**
  corriendo (`1-17:28:36`) con 3,3 GB de memoria.
- Ese servidor es el que sirve la API, la web y las herramientas de Emilio, y se ha saturado varias
  veces. Liberar 1,2 núcleos y 4 GB ahí es dinero directo.
- StrategyQuant ya vive en el servidor nuevo (Hetzner), con **más proyectos** que el viejo y 446 MB
  de datos de usuario. Ese pasa a ser el bueno.

**Cuidado, y esto es lo importante de la tarea:** apagar el proceso NO basta. `CLAUDE.md:32-35` avisa
de que el servicio está `enabled` (systemd lo relanza solo) y de que un cron lo revive cada 20-30
minutos. **Hacen falta las tres acciones**, o en media hora vuelve a estar corriendo.

## Qué hacer

**Paso 0, antes de tocar nada: comprobar que no perdemos datos.** El banco `ToImprove` del proyecto
`Ultra_Matrix` en Oracle tiene 3.474 estrategias. Antes de apagar, comprueba que el Hetzner tiene ese
proyecto:

```bash
ssh sqx-hetzner 'ls /opt/StrategyQuantX/user/projects/ | head -30; du -sh /opt/StrategyQuantX/user/projects/Ultra_Matrix 2>/dev/null'
```

Si `Ultra_Matrix` **no** está en el Hetzner o pesa mucho menos que en Oracle (allí ocupa 173 MB),
**para aquí**, pon la tarea en `BLOQUEADO` y dilo: habría que copiar los datos antes. No apagues nada.

**Paso 1: fotografía del estado actual, para poder comparar después.**

```bash
ssh oracle-vps 'uptime; free -m | sed -n 2,3p; ps -eo pid,etime,%cpu,rss,cmd | grep -E "sqcli|StrategyQuant" | grep -v grep'
```

**Paso 2: las tres vías, en este orden.**

```bash
ssh oracle-vps 'sudo -n systemctl stop sqx.service; sudo -n systemctl disable sqx.service; systemctl is-active sqx.service; systemctl is-enabled sqx.service'
```

```bash
ssh oracle-vps 'crontab -l > /tmp/crontab.backup.$(date -u +%Y%m%d%H%M) && crontab -l | sed "s|^40 \* \* \* \* nice|#40 * * * * nice|" | crontab - && crontab -l | grep -n improve_cycle'
```

La línea del cron queda **comentada, no borrada**, y con copia de seguridad en `/tmp`. Si la línea no
empieza exactamente por `40 * * * *`, **no improvises con el `sed`**: pega lo que veas en el parte y
para. Es preferible dejarlo a medias que estropear el cron de Emilio.

**Paso 3: foto inmediata y se acabó.** NO esperes. Haz la comprobación ahora mismo y entrega:

```bash
ssh oracle-vps 'ps -eo pid,cmd | grep -E "sqcli|StrategyQuant" | grep -v grep || echo "SQX NO ESTA CORRIENDO"; uptime; free -m | sed -n 2,3p'
```

De comprobar dentro de media hora que no ha resucitado se encarga el orquestador, que para eso tiene
vigilantes. **Tú no esperas a nada: entregas y coges la tarea siguiente.**

otros servicios; parar el StrategyQuant del Hetzner, que es el bueno; usar `rm`.
