## Por qué

He abierto la comparativa como la abriría Emilio y esto es lo que sale:

```
$ curl "…/api/v2/candidates/censo"
estrategias que devuelve : 250
marcadas como candidatas :   1
rentabilidad anual       : mediana -1,14 %   maximo 0,61 %
```

**Mediana negativa y una sola candidata.** Justo esta noche hemos medido que hay **225 extraíbles**
en una sola celda, 32 de ellas por encima del 2 % mensual, y la mejor con un **68 % anual**. Nada de
eso se ve. Emilio abriría esa página y pensaría, con razón, que el sistema no produce.

Dos causas, las dos concretas:

**1. Las estrategias buenas no están en el censo.** `FONDEO_MGC_H4` tiene 2.000 filas y **las 2.000
se midieron con la regla vieja**:
```
$ por capital con el que se midieron:  {100000: 2000}
```
Las 581 de la ronda 3, las del dimensionamiento nuevo (mediana 11,22 % anual), **no se han
sincronizado**. Existen en el CSV del servidor y en 46.537 artefactos, pero no en la base de datos
que alimenta la web.

**2. La tabla no ordena: coge las 250 primeras de la base de datos.**
```python
# candidates_router.py:203
for r in fondeo_rows[:limite]:
```
Sin `order_by`. O sea que Emilio ve un trozo arbitrario, y por eso la mediana sale negativa. (Otros
endpoints del mismo fichero sí ordenan, `:384` y `:502`, así que el patrón ya existe en casa.)

## Qué hacer

**1. Sincronizar la ronda 3 al censo**, con la marca de dimensionamiento nuevo que ya montaste en
A51. Que entren las 581 de `FONDEO_MGC_H4` y las de cualquier otra celda que haya cerrado ronda con
la regla nueva. Comprueba después que en el censo conviven las dos marcas y que la tabla lo avisa.

**2. Que la comparativa ordene, y que ordene por lo que importa.** Por defecto, **las mejores
primero**, y "mejor" aquí es **rentabilidad con la caída dentro de límite**, no rentabilidad a secas.
Propuesta, y si se te ocurre mejor dilo en el parte: ordenar por rentabilidad anual fuera de muestra
**descendente**, pero **primero las etiquetadas "apta para operar", luego "apta para mejorar", luego
"con promesa"**. Y que el usuario pueda ordenar por cualquier columna con un clic, que eso ya estaba.

**3. Las tres etiquetas, calculadas y visibles**, con los umbrales que están escritos en A52:

| Etiqueta | Rentabilidad mensual | Caída (% de una cuenta de 50.000) |
| :--- | :--- | :--- |
| **Apta para operar** | ≥ 2 % | < 6 % |
| **Apta para mejorar** | ≥ 2 % | 6 – 12 % |
| **Con promesa** | 1 – 2 % | ≤ 12 % |
| *(sin etiqueta)* | el resto | |

Que la etiqueta se calcule al servir, **no** se escriba en la base de datos: los umbrales van a ser
editables desde el panel (A52) y no quiero tener que recalcular cinco mil filas cada vez que Emilio
mueva un número.

**4. Un resumen arriba, de una línea**, con lo que hay: *"6.748 estrategias · 32 aptas para operar ·
36 aptas para mejorar · 157 con promesa"*. Es lo primero que Emilio mira.

## Aceptación

```bash
# 1) las nuevas estan dentro y con su marca
python -c "cuenta filas de MGC_H4 por capital del sizing"    # deben aparecer las de 50000

# 2) la comparativa ya no abre en negativo
curl -s "http://127.0.0.1:8100/api/v2/candidates/censo?limite=20" | grep -o '"annual_return_oos_pct":[^,]*' | head -5
#    -> las primeras deben ser las mejores, no un trozo al azar

# 3) las etiquetas salen
curl -s "http://127.0.0.1:8100/api/v2/candidates/censo?limite=5" | grep -c "etiqueta"     # 5

# 4) y el resumen en la pagina
curl -s http://127.0.0.1:3100/estrategias/candidatos | grep -cE "aptas para operar|apta para operar"   # > 0

# 5) reinicia la API y vuelve a pasar 2) y 3) contra el proceso nuevo
```

## Prohibido

Escribir la etiqueta en la base de datos (se calcula al servir). Ordenar por el resultado del tramo
reservado para **seleccionar** qué se extrae —ordenar la vista sí, seleccionar no—. Borrar filas
viejas: conviven marcadas. Dar por buena la aceptación sin reiniciar la API.

mejor estrategia de la casa arriba del todo, con su 68 % anual y su 3,3 % de caída. Hoy ve una
mediana negativa.
