## Por qué

El fichero `apps/web/app/api/local/superadmin/route.ts` fue reescrito y tiene **dos fallos graves**.
El primero deja entrar a quien no debe; el segundo hace que el superadministrador no sea quien es.

**Fallo 1: cualquiera puede activarse como superadministrador falseando una cabecera.**

```ts
function esHostLocal(host: string | null): boolean {
  ...
  const esPuerto3100 = host.includes("3100");
  return esLocal || esPuerto3100;
}
const variableActiva = process.env.ULTRARENTABLE_LOCAL_SUPERADMIN === "1" || local;
if (!variableActiva && !local) { ... }
```

Dos problemas encadenados. El `host` de una petición **lo elige quien la hace**: no es un dato de
confianza. Basta mandar una cabecera `Host: cualquiercosa:3100` contra el servidor público para que
`esHostLocal` devuelva verdadero. Y como `variableActiva` ya incluye `|| local`, la variable de
entorno deja de pintar nada: la condición de seguridad que separaba el PC del servidor público ha
desaparecido. El resultado es que la ruta puede devolver `enabled: true` con perfil
`is_superadmin: true` a un desconocido.

El diseño original tenía dos condiciones **independientes y obligatorias**: una variable de entorno
que solo existe en el fichero `.env.local` del PC (que no se sube al repositorio) **y** un host
local. Así el mismo build servido en el servidor público no activa nada nunca, porque allí la
variable no existe. Hay que volver a eso.

**Fallo 2: el correo del superadministrador está mal escrito.**

```ts
export const SUPERADMIN_EMAIL = "ferestudio@gmail.com";
```

El correo real es **josferestudio@gmail.com**, y así está en todo el proyecto:
`apps/web/context/AuthContext.tsx:30` (`export const SUPERADMIN_EMAIL = "josferestudio@gmail.com"`),
`apps/web/app/perfil/page.tsx:308`, `apps/web/components/layout/AppShell.tsx:223`. Ahora hay dos
constantes con el mismo nombre y valores distintos en el mismo proyecto, que es la peor forma de
tener un bug: funciona hasta que alguien compara los dos. Además `ferestudio@gmail.com` es una
dirección de otra persona, o de nadie.

## Qué hacer

1. `esHostLocal` vuelve a aceptar **solo** `localhost`, `127.0.0.1`, `::1` y `[::1]`, ignorando el
   puerto. Quita `host.includes("3100")`: el puerto no dice nada sobre quién pregunta.
2. La condición vuelve a ser **las dos cosas a la vez**:
   `process.env.ULTRARENTABLE_LOCAL_SUPERADMIN === "1"` **Y** host local. Si falta cualquiera de las
   dos, `enabled: false` con el motivo concreto (cuál de las dos falla), que ayuda a diagnosticar.
3. El correo pasa a `josferestudio@gmail.com`. No declares una constante nueva: **importa**
   `SUPERADMIN_EMAIL` de `@/context/AuthContext` si el import funciona desde una ruta de servidor;
   si no funciona, deja la constante local con el valor correcto y un comentario que diga que el
   original vive en `AuthContext.tsx` y que los dos deben coincidir. Elimina `SUPERADMIN_EMAILS`:
   dos correos válidos para el superadministrador es una puerta de más sin motivo.
4. La cookie `ultra_local_admin` puedes conservarla: no da acceso por sí sola, quien decide es el
   servidor en cada petición. Pero ponle `httpOnly: false` solo si algo la lee desde el navegador; si
   no la lee nadie, déjala `httpOnly: true`. Comprueba con `grep -rn "ultra_local_admin" apps/web`
   antes de decidir, y explica en el parte qué encontraste.

## Aceptación

```bash
grep -n "includes(\"3100\")" apps/web/app/api/local/superadmin/route.ts     # esperado: sin resultados
grep -n "josferestudio@gmail.com" apps/web/app/api/local/superadmin/route.ts # esperado: 1 linea
grep -rn "ferestudio@gmail.com" apps/web --include=*.ts --include=*.tsx | grep -v josferestudio   # esperado: sin resultados
cd apps/web && ../../node_modules/.bin/tsc --noEmit -p tsconfig.json         # rc=0
curl -s http://127.0.0.1:3100/api/local/superadmin                           # enabled:true, email josferestudio@gmail.com
curl -s -H "Host: pirata.example.com:3100" http://127.0.0.1:3100/api/local/superadmin   # esperado: enabled:false
```

Ese último comando es el que importa: **con una cabecera Host falseada tiene que responder
`enabled: false`**. Pega su salida completa en el parte.

## Prohibido

Tocar `apps/web/context/AuthContext.tsx` (el correo bueno ya está bien ahí); cambiar el fichero
`.env.local`; quitar la ruta; ampliar la lista de correos autorizados.
