## Why this order exists
The previous Phase 01 handoff is not accepted as certification-grade because the DatasetRegistry contains evidence fabrication/fallback behavior that violates REAL-ONLY / ZERO-SIMULATION.

## Required corrections

### P01-REWORK-01 — Physical partition hashes
Partition SHA-256 values MUST be calculated from the actual bytes/content of each partition, not from synthetic strings or metadata labels.

For every partition:
- materialize the exact records/bytes belonging to the partition;
- canonicalize deterministically;
- compute SHA-256 over the canonical partition payload;
- store the hash and record count;
- prove the same input bytes reproduce the same hash.

### P01-REWORK-02 — Remove invented metadata defaults
Remove operational defaults that manufacture provenance/evidence, including:
- `source_id` fallback such as `YAHOO_CME` when source is absent;
- invented timestamps such as `start_ms=1` or `end_ms=start_ms+86400000`;
- `coverage_pct=100.0` when coverage is unknown;
- silent manifest completion from incomplete metadata without recording its provenance.

Missing/unknown values must be `UNVERIFIED`, `NO_EVIDENCE`, or explicit failure according to the canonical contract.

### P01-REWORK-03 — Physical integrity checks
The registry must verify, from physical bytes:
- row/bar count;
- monotonic timestamps;
- duplicates;
- out-of-order records;
- actual start/end coverage;
- gap counts where deterministically computable;
- schema/columns;
- timezone normalization;
- file SHA-256.

No claim may rely solely on stale manifest metadata if current bytes contradict it.

### P01-REWORK-04 — Partition boundary correctness
Partition definitions must correspond exactly to physical record boundaries or an explicitly documented deterministic timestamp rule.

Do not use invented time ranges unrelated to actual record boundaries. The registry must be able to prove that IS / Validation / Blind OOS records are disjoint and exhaustive for the defined dataset snapshot.

### P01-REWORK-05 — Fail-closed loader
`load_dataset_bars()` must fail closed when:
- dataset missing;
- file hash mismatch;
- manifest identity mismatch;
- malformed data;
- unresolved partition metadata;
- unverifiable provenance required for the operation.

Never silently substitute another dataset.

### P01-REWORK-06 — Dataset registry resolution
Resolution must be registry-driven and deterministic. Remove fuzzy symbol matching where it can silently resolve an unintended instrument. Ambiguity must return `NO_EVIDENCE` / explicit error.

### P01-REWORK-07 — Evidence manifest reproducibility
Every generated manifest must identify at minimum:
`data_snapshot_id, source_id, instrument_id, timeframe_id, schema_version, normalization_version, start, end, record_count, file_sha256, partition definitions, partition hashes`.

No field may be invented to make a manifest look complete.
