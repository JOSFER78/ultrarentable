No necesitas una herramienta: necesitas una fábrica completa de estrategias

NautilusTrader debe ser el motor canónico de simulación y ejecución, pero no es el buscador. La solución funcional combina investigación automática, generación de reglas, búsqueda evolutiva, optimización numérica, un motor rápido, validación L2 en NautilusTrader, un segundo comprobador independiente y una escalera testnet → shadow → micro-live.

Mejor arquitectura para tu caso

RD-Agent/LLM investigador + DSL tipada + DEAP + VectorBT + Optuna + Ray + NautilusTrader + datos Hyperliquid/Tardis + validador independiente. StrategyQuant X o Build Alpha pueden aportar semillas, pero no deben decidir qué estrategia es real.

Regla de selección
Sobrevive + crece

Solo invalidan: equity ≤ 0, liquidación, datos futuros, fills imposibles o experimento irreproducible. El drawdown se observa, pero no filtra.

1. Definir correctamente el objetivo de 1000%

El buscador necesita un objetivo matemático exacto para que todos los motores midan lo mismo.

Calculadora del objetivo

Capital final11.000 €
Multiplicador11,0×
CAGR equivalente—

Una ganancia de +1000% convierte el capital en 11×. Multiplicar por 10 equivale a +900%.

Función objetivo recomendada

valid = simulation_ok and min_equity > 0 and not liquidated

if not valid:
    score = -infinity
else:
    score = log(final_equity / initial_equity)

target_return_pct = 1000
target_equity_multiple = 11.0
No añadas Sharpe, drawdown o estabilidad al score principal. Mantén un “nivel de evidencia” separado para saber si el 1000% proviene de una oportunidad reproducible, de un régimen concreto o de un artefacto.

4. Cómo buscar y crear estrategias

Se necesitan tres fábricas paralelas que entreguen el mismo formato de estrategia.

Agente de fuentes

Busca papers, repositorios, competiciones, documentación, foros técnicos y estrategias públicas. Guarda fuente, fecha, mercado, inputs disponibles y posible fuga de información.

Agente de formalización

Convierte una idea narrativa en reglas exactas: entrada, salida, temporalidad, apalancamiento, tamaño, órdenes y datos requeridos.

Agente replicador

Implementa la versión base sin optimizar, la compara con lo publicado y documenta por qué coincide o difiere.

hypothesis_card:
  source_url: "..."
  published_at: "..."
  market: "ETH perpetual"
  mechanism: "liquidation cascade continuation"
  required_inputs: [trades, l2, mark_price, open_interest]
  entry_logic: "..."
  exit_logic: "..."
  falsification_test: "..."
  leakage_risks: ["..."]
  status: NEW

Gramática tipada

Bloques válidos por construcción: precio con precio, booleanos con booleanos y ventanas solo con valores anteriores.

Programación genética

DEAP permite árboles fuertemente tipados. Mutación de nodos, cruces de subárboles y límites de profundidad evitan código arbitrario.

Novedad controlada

El agente puede proponer nuevos bloques, pero deben pasar pruebas unitarias y de look-ahead antes de entrar en la gramática.

strategy_tree = AND(
    BREAKOUT(high, lookback=36, lag=1),
    GT(volume_ratio(30), 1.8),
    REGIME(volatility_percentile(120), min=0.72)
)

mutation_space = {
  lookback: 4..240,
  threshold: 0.1..5.0,
  leverage: 1..venue_max,
  pyramiding_entries: 0..8,
  exit_family: [time, atr, trailing, reverse, partial]
}

StrategyQuant X

Importar OHLCV/funding como datos, generar poblaciones y exportar las reglas. Después traducirlas a la DSL y repetir todo en tus motores. Su resultado nunca entra directamente al ranking canónico.

Build Alpha

Útil para incorporar señales Python personalizadas, combinarlas mediante búsqueda genética y exportar estrategias. La mejor opción comercial para señales propias; sigue siendo un proveedor de semillas.

Regla: toda estrategia importada pierde sus métricas originales. En el laboratorio comienza de cero y recibe nuevos resultados con tus datos, costes, liquidación y orden de eventos.

5. Familias que merece la pena explorar para retornos extremos

No son promesas de rentabilidad; son espacios donde el payoff puede ser muy convexo.

PRIORIDAD A

Ruptura explosiva

Compresión → expansión de volatilidad, volumen anómalo, confirmación L2 y piramidación solo a favor.

PRIORIDAD A

Cascadas de liquidación

Continuación o reversión tras desequilibrio, trades agresores, caída de OI y desplazamiento del mark.

PRIORIDAD A

Momentum por régimen

Activación temporal cuando volatilidad, dirección, funding y OI forman un régimen poco frecuente.

PRIORIDAD A

Piramidación convexa

Añadir exposición únicamente cuando la posición ya está financiada por beneficio abierto y el flujo sigue confirmando.

PRIORIDAD B

Extremos de funding

Contrarian, continuación o carry direccional condicionado por precio, basis, OI y velocidad del funding.

PRIORIDAD B

Microestructura L2

Imbalance, agotamiento de niveles, spread, profundidad y aceleración de agresores. Requiere datos granulares.

PRIORIDAD B

Eventos y horarios

Ventanas recurrentes, anuncios, aperturas de sesiones o shocks de mercado; estrategias especializadas y apagadas fuera del evento.

PRIORIDAD B

Ensemble adaptativo

Varias estrategias kamikaze pequeñas; un selector de régimen elige cuál activar, sin promediar señales incompatibles.

No optimizar todo a la vez. Primero mecanismo de entrada, después salida, luego ejecución y finalmente apalancamiento/compound. Si se mezclan desde el principio, el motor encontrará multiplicadores enormes sin que puedas saber qué los causa.

6. Motor de optimización y mejora

La búsqueda debe alternar amplitud, explotación de ganadores y ataques adversariales.

40%

Exploración

Random/QMC y generación genética para descubrir familias que no provienen de los ganadores actuales.

40%

Explotación

TPE para espacios mixtos; CMA-ES para parámetros continuos alrededor de una familia prometedora.

20%

Mutaciones radicales

Cambiar familia de salida, régimen, orden o sizing para escapar de máximos locales.

Bucle recomendado

for generation in campaign:
    ideas = research_agent.propose(memory, failures, market_regimes)
    population = gp_factory.create(ideas, parents, novelty_budget)

    fast = vector_engine.run(population, discovery_windows)
    top = rank(valid_survivors(fast), by="final_equity")

    tuned = optuna_refine(top, samplers=["TPE", "CMA_ES"])
    canonical = ray_map(nautilus_l2_backtest, tuned[:budget])

    audited = independent_replay(canonical.top_n)
    memory.store_all(population, fast, canonical, audited)
    parents = select_by_return_and_novelty(canonical)

Memoria para no repetir errores

  • Hash de la estructura y parámetros.
  • Padres, mutación, fuente y agente.
  • Versión exacta de datos y motor.
  • Todas las ventanas probadas, también las malas.
  • Razón técnica de invalidación.
  • Huella de operaciones y equity curve.
  • Número total de candidatos probados: imprescindible para medir selección múltiple.
Importante: PBO, Deflated Sharpe, CPCV y sensibilidad no tienen que bloquear candidatos en tu modo Kamikaze. Deben mostrarse como evidencia separada para distinguir un 1000% creíble de un 1000% encontrado por probar millones de combinaciones.

7. Datos: ruta gratuita, barata y profesional

La calidad del backtest depende más del dato y del modelo de fills que del nombre del motor.

RUTA 0

Archivo oficial Hyperliquid

El bucket S3 oficial publica snapshots L2 aproximadamente una vez al mes. El requester paga transferencia; puede haber huecos y no se garantiza puntualidad.

Uso: base L2 inicial y auditoría contra datos de terceros.

RUTA 1

Grabador propio 24/7

WebSocket de trades, l2Book, mark, funding, OI y estado del venue. Guardar ts_event y ts_init para medir latencia real.

Uso: shadow y mejora continua.

RUTA PRO

Tardis → Nautilus

Replay granular, snapshots/deltas L2, trades, funding, mark/index y OI normalizados directamente a Parquet de Nautilus.

Uso: histórico limpio y cómodo; requiere suscripción salvo el primer día de cada mes.

8. NautilusTrader: qué hará exactamente

Última versión localizada: 1.227.0 Beta, publicada el 18 de mayo de 2026. Debe fijarse por versión y probarse antes de producción.

Mismo modelo de sistema

La estrategia, actores y algoritmos de ejecución pueden usarse en backtest y live sin reescribir la lógica principal.

Matching L2/L3

Las órdenes market recorren niveles; los límites descansan; se modelan parciales, latencia, cola y consumo de liquidez.

Hyperliquid oficial

Adaptador Rust con REST/WebSocket, datos live, cuenta y ejecución. Testnet y mainnet usan la misma arquitectura.

Configuración canónica mínima

venue = BacktestVenueConfig(

    # fee, latency, margin and fill configs versioned
)

Limitaciones que el informe no oculta

  • El histórico es inmutable; tus órdenes no cambian el mercado pasado.
  • La posición exacta en la cola nunca se conoce; se aproxima.
  • Si faltan deltas o trades, la simulación no puede inventarlos.
  • Testnet no replica la liquidez de mainnet.
  • La versión actual está etiquetada Beta.
  • Un fill model optimista puede inflar radicalmente una estrategia apalancada.
Configuración obligatoria: activar consumo de liquidez, usar L2 + trades para finalistas, modelar latencia medida, aplicar fees/funding y reproducir la liquidación de Hyperliquid con mark price y margin tiers.

11. Testnet, shadow y micro-live

Esta fase mide la diferencia real entre el backtest y la operativa, no busca “proteger” la estrategia.

PASO 1

Replay live

Consumir mainnet en tiempo real; decidir y simular órdenes localmente sin enviarlas.

PASO 2

Testnet

Validar autenticación, tipos de orden, rejects, reconexiones, reconciliación y estado de cuenta.

PASO 3

Shadow mainnet

Comparar precio teórico, precio ejecutable, profundidad y latencia real. No confundir con testnet.

PASO 4

Micro-live

Orden mínima real para calibrar fills, fees, latencia, cancelaciones y diferencias de mark/funding.

Promoción automática correcta: no exige drawdown bajo. Exige que el sistema técnico funcione, que las órdenes sean válidas y que la divergencia observada pueda incorporarse al modelo de simulación.

Conclusión ejecutiva

La solución no es “NautilusTrader solo”. Es una fábrica abierta donde los agentes y la programación genética crean estrategias, VectorBT y Optuna exploran, Ray escala, NautilusTrader decide qué ocurrió bajo una simulación granular, un segundo motor busca errores y Hyperliquid testnet/mainnet mide la divergencia. El objetivo ≥1000% se mantiene como prioridad absoluta; la fiabilidad se informa en una dimensión separada, sin reintroducir filtros de drawdown.
